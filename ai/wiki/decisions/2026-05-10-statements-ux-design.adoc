= ADR: Projekt UX oświadczeń i szablonów kwalifikacji w interfejsie Hexabid SPA
:toc: macro
:toclevels: 3
:sectnums:

toc::[]

== Tytuł

Redesign interfejsu użytkownika Hexabid SPA: integracja systemu oświadczeń kandydatów, szablonów polityki dopuszczenia i konfiguracji aukcji w spójny, intuicyjny proces dla sprzedającego i licytanta.

== Podsumowanie (TLDR)

Obecny interfejs Hexabid SPA nie korzysta z gotowego backendu oświadczeń (`ParticipationApi` jest wygenerowany, ale nieużywany). Formularz tworzenia aukcji jest płaski i nie pozwala na wybór szablonu kwalifikacji. Licytant nie ma żadnej ścieżki do przejścia przez oświadczenia przed licytacją.

Proponuję trzy kluczowe zmiany UX:

. **Sprzedający**: Przejście z płaskiego formularza na **wizard krokowy** (4 kroki: Podstawy → Format i kwalifikacja → Konfiguracja ceny → Podsumowanie), gdzie krok 2 pozwala wybrać `AuctionFormat` i `ParticipationPolicyTemplate`.
. **Licytant**: Dodanie **bramki kwalifikacji** (`ParticipationGate`) na stronie szczegółów aukcji -- licytant musi przejść przez oświadczenia zanim zobaczy formularz licytacji.
. **Oświadczenia**: **Guided statement wizard** sterowany grafem DAG z backendu -- pokazuje tylko dostępne oświadczenia, grupuje je w kroki, daje natychmiastowy feedback, obsługuje odrzucenie z wyjaśnieniem kaskady.

== Diagnoza obecnego stanu

=== Co działa

| Aspekt | Stan |
|--------|------|
| Backend oświadczeń | W pełni zaimplementowany: 3 szablony, DAG, ewaluator, REST API, JPA, testy integracyjne |
| OpenAPI contract | Zdefiniowane 4 endpointy Participation + wszystkie modele |
| TypeScript codegen | `ParticipationApi`, `StatementProgramView`, `SubmitStatementAnswerResponse` wygenerowane |
| Rules panel | Pokazuje fazy PARTICIPATION/BIDDING/SETTLEMENT z naruszeniami |
| Bidding real-time | STOMP WebSocket z live feed |
| Dokumenty | Formularz zgłaszania dokumentów (excise, customs, etc.) |

=== Co nie działa

| Aspekt | Problem |
|--------|---------|
| Participation API | Wygenerowana, ale **zero użycia** w kodzie ręcznym |
| Tworzenie aukcji | Płaski formularz, brak wyboru `AuctionFormat` ani `ParticipationPolicyTemplate` |
| Ścieżka licytanta | Brak jakiejkolwiek ścieżki kwalifikacji przed licytacją |
| Integracja rules ↔ statements | Rules panel pokazuje PARTICIPATION violations, ale nie linkuje do wizardu oświadczeń |
| Buy-now price | Model istnieje w `CreateAuctionRequest`, ale nie ma pola w UI |
| Lot assignment | Brak w UI |

=== Diagnoza UX

Obecny flow jest **rozlany i niekierowany**:

1. Sprzedający tworzy aukcję jednym formularzem -- nie wie, że może skonfigurować wymagania dla licytantów.
2. Licytant widzi formularz licytacji od razu, nawet jeśli nie przeszedł kwalifikacji.
3. Rules panel mówi "masz blokady w PARTICIPATION", ale nie mówi CO Z TYM ZROBIĆ.
4. Dokumenty i oświadczenia to dwa różne byty, ale w UI nie ma tego rozróżnienia.

== Zasady projektowe

=== 1. Progressive Disclosure

Nie pokazuj złożoności, dopóki użytkownik jej nie potrzebuje.

* Dla prostej aukcji konsumenckiej: 2 pola + wybór szablonu z podpowiedzią.
* Dla przetargu regulowanego: pełna konfiguracja z wyjaśnieniem każdego wymogu.

=== 2. DAG-Driven UI

Graf zależności z backendu **steruje** interfejsem, nie odwrotnie.

* Backend mówi: "te oświadczenia są dostępne" → UI je pokazuje.
* Backend mówi: "te oświadczenia są zablokowane" → UI je ukrywa z wyjaśnieniem.
* Backend mówi: "odpowiedź dyskwalifikująca" → UI zatrzymuje proces z powodem.

=== 3. Goal-Oriented Navigation

Każdy ekran powinien odpowiadać na pytanie: "co chcę osiągnąć i jak?"

* Licytant: "Chcę licytować" → "Najpierw musisz przejść kwalifikację" → "Oto Twoje oświadczenia do złożenia"
* Sprzedający: "Chcę wystawić aukcję" → "Jaki to typ aukcji?" → "Jakie wymagania dla licytantów?"

=== 4. Graceful Rejection

Odrzucenie nie jest błędem -- to informacja. Zawsze pokazuj:

* CO się stało (które oświadczenie, która odpowiedź)
* DLACZEGO ma to znaczenie (jaka reguła, jaki skutek)
* CO DALEJ (czy jest odwołanie, czy trzeba zacząć od nowa, czy nic nie da się zrobić)

=== 5. Consistent Mental Model

Oświadczenia ≠ dokumenty ≠ reguły, ale są powiązane:

| Pojęcie | Co robi użytkownik | Kiedy | Gdzie w UI |
|---------|-------------------|-------|------------|
| Oświadczenie | Deklaruje fakt o sobie | Przed licytacją (PARTICIPATION) | Statement wizard |
| Dokument | Dostarcza dowód | Na każdym etapie | Document submit form |
| Reguła | System weryfikuje warunek | Automatycznie | Rules panel |

== Projekt: Sprzedający -- Wizard tworzenia aukcji

=== Obecny flow

```
/sell → [Płaski formularz: tytuł, cena, data, opcjonalna konfiguracja ceny] → Zapisz → /auction/:id
```

=== Proponowany flow

```
/sell → Krok 1: Podstawy → Krok 2: Format i kwalifikacja → Krok 3: Konfiguracja ceny → Krok 4: Podsumowanie → Zapisz → /auction/:id
```

=== Krok 1: Podstawy (Basics)

.Nazwa aukcji (title) -- wymagane, min 4 znaki
.Cena wywoławcza (startingPrice) -- kwota + waluta
.Koniec aukcji (endsAt) -- datetime-local
.Cena "Kup teraz" (buyNowPrice) -- opcjonalne, kwota + waluta

Racjonalizacja: To absolutne minimum, żeby aukcja miała sens. Bez tytułu, ceny i terminu nie da się wystawić aukcji. Buy-now jest opcjonalne -- istnieje w modelu, ale nie było w UI.

=== Krok 2: Format i kwalifikacja (Format & Admission)

==== Auction Format

Wybór mechaniki aukcji:

| Wartość | Label PL | Opis |
|---------|----------|------|
| `ENGLISH_ASCENDING` | Angielska (rosnąca) | Standardowa licytacja z rosnącymi ofertami |
| `DUTCH_DESCENDING` | Holenderska (malejąca) | Cena spada, pierwszy kto zaakceptuje wygrywa |
| `SEALED_BID` | Przetarg zamknięty | Jednorazowa ukryta oferta, najlepsza wygrywa |
| `RESTRICTED_TENDER` | Przetarg ograniczony | Tylko zaproszeni kandydaci mogą licytować |

==== Participation Policy Template

Wybór poziomu kwalifikacji licytantów:

| Szablon | Label PL | Opis UI | Ilość oświadczeń |
|---------|----------|---------|------------------|
| `PUBLIC_CONSUMER_LIGHT_V1` | Publiczna konsumencka | "Lekka weryfikacja -- 4 oświadczenia, szybka ścieżka dopuszczenia. Idealna dla aktywów niskiego ryzyka: elektronika, kolekcjonerstwo, dobra konsumenckie." | 4 |
| `REGULATED_ASSET_BUYER_V1` | Majątek regulowany | "Weryfikacja regulowana -- 8 oświadczeń z weryfikacją licencji, kontroli eksportu i zdolności środowiskowej. Dla alkoholu, paliw, odpadów, urządzeń specjalistycznych." | 8 |
| `HIGH_VALUE_TENDER_V1` | Przetarg wysokiej wartości | "Pełna weryfikacja AML/antykoluzja -- 11 oświadczeń z ujawnieniem PEP, źródłem środków i poufnością data room. Dla nieruchomości, floty, maszyn, pakietów przedsiębiorstwa." | 11 |

==== UX szczegóły

* Każdy szablon pokazany jako **karta** (card) z ikoną, tytułem, opisem i liczbą oświadczeń.
* Po najechaniu (hover) lub kliknięciu "Szczegóły" -- rozwinięcie z listą kroków i oświadczeń.
* Domyślnie wybrany `PUBLIC_CONSUMER_LIGHT_V1` (najprostszy).
* Jeśli `AuctionFormat = SEALED_BID` -- podpowiedź: "Przetarg zamknięty często wymaga wyższego poziomu kwalifikacji. Rozważ REGULATED_ASSET_BUYER_V1 lub HIGH_VALUE_TENDER_V1."
* Jeśli `AuctionFormat = RESTRICTED_TENDER` -- podpowiedź: "Przetarg ograniczony wymaga dopuszczenia. Wybierz co najmniej REGULATED_ASSET_BUYER_V1."

=== Krok 3: Konfiguracja ceny (Pricing Config)

Identyczny jak obecna sekcja "Dodaj konfigurację ceny", ale jako osobny krok zamiast collapsible section:

* Strategia wadium (brak / procentowe / stałe)
* Stawka VAT
* Produkt akcyzowy + stawka i typ
* Produkt importowany + stawka cła

Racjonalizacja: Przeniesienie z collapsible do osobnego kroku zmniejsza cognitive load na kroku 1 i daje równą wagę konfiguracji finansowej.

=== Krok 4: Podsumowanie (Review)

Widok read-only z wszystkimi wybranymi opcjami:

* Podstawy: tytuł, cena, termin, buy-now
* Format: wybrany format z opisem
* Kwalifikacja: wybrany szablon z listą oświadczeń
* Cena: konfiguracja VAT/wadium/akcyza/cło
* Przycisk "Zapisz szkic aukcji" lub "Wstecz" do edycji

Racjonalizacja: Podsumowanie daje sprzedającemu ostatnią szansę na weryfikację przed utworzeniem szkicu. Jest to standard UX w e-commerce i formularzach wielokrokowych.

=== Nawigacja wizarda

* Stepper na górze strony: `① Podstawy → ② Format i kwalifikacja → ③ Cena → ④ Podsumowanie`
* Przyciski "Dalej" i "Wstecz" na każdym kroku
* "Dalej" waliduje bieżący krok przed przejściem
* "Wstecz" zachowuje stan formularza
* Bezpośredni klik na numer kroku pozwala na powrót do zatwierdzonego kroku

== Projekt: Licytant -- Bramka kwalifikacji

=== Obecny flow

```
/auction/:id → [Formularz licytacji od razu widoczny] → Licytuj
```

Problem: Licytant widzi formularz licytacji nawet jeśli nie jest dopuszczony do aukcji. Rules panel mówi o blokadach PARTICIPATION, ale nie daje akcji.

=== Proponowany flow

```
/auction/:id
  → [Czy licytant ma zakończony program oświadczeń?]
    → NIE: Bramka kwalifikacji → Statement wizard → Decyzja → [Jeśli ADMITTED] → Formularz licytacji
    → TAK (ADMITTED): Formularz licytacji od razu
    → TAK (REJECTED): Ekran odrzucenia z wyjaśnieniem
    → TAK (PENDING): Informacja o brakach + link do uzupełnienia
```

== Projekt: Statement Wizard

=== Architektura komponentu

Wizard jest **sterowany z backendu** -- każdy krok i każde oświadczenie pochodzi z `StatementProgramView`, nie jest hardcodowane w UI.

=== Widok kroku

Każdy krok (`StatementStep`) to grupa oświadczeń z tym samym `order` i `stepLabel`:

=== Interakcja z oświadczeniem

Każde oświadczenie (`StatementStepView`) jest renderowane na podstawie `answerType`:

| `answerType` | Komponent UI | Walidacja |
|--------------|-------------|-----------|
| `YES_NO` | Dwa radio buttony: "Tak" / "Nie" | Wymagany wybór |
| `TEXT` | Textarea | Wymagany niepusty tekst |
| `SINGLE_CHOICE` | Radio group z opcjami | Wymagany wybór |
| `MULTI_CHOICE` | Checkbox group z opcjami | Wymagany co najmniej jeden |
| `NUMERIC` | Input number | Wymagana wartość numeryczna |
| `DOCUMENT_UPLOAD` | File upload + status | Wymagany plik |

Po kliknięciu "Potwierdź":

1. Wywołanie `POST /api/auctions/{auctionId}/participation/statements/{statementCode}/answers`
2. Obsługa trzech wyników:
   - `ACCEPTED`: Odśwież program, odblokuj następne oświadczenia, zaktualizuj pasek postępu.
   - `REJECTED`: Zatrzymaj wizard, pokaż ekran odrzucenia z powodem i kaskadą.
   - `PREREQUISITE_NOT_MET`: Błąd walidacji -- pokaż które prerekwizyty brakują.

=== Przepływ danych

....
1. startParticipationProgram(auctionId, templateName)
   → StatementProgramView { availableStatements, completedStatements, blockedStatements, decision }

2. Dla każdego dostępnego oświadczenia:
   submitStatementAnswer(auctionId, statementCode, answerValue)
   → SubmitStatementAnswerResponse { resultType, reason, missingPrerequisites, program }

3. Po każdej odpowiedzi:
   - Jeśli ACCEPTED: odśwież program → pokaż nowo dostępne oświadczenia
   - Jeśli REJECTED: zatrzymaj wizard → pokaż ekran odrzucenia
   - Jeśli PREREQUISITE_NOT_MET: pokaż błąd walidacji

4. Na żądanie:
   getParticipationDecision(auctionId)
   → ParticipationDecisionView { status, rootCause, humanReason, missingStatements, cascadedStatements, conditions }
....

== Projekt: Integracja z istniejącymi komponentami

=== Rules Panel ↔ Participation Gate

Obecny rules panel pokazuje fazy PARTICIPATION/BIDDING/SETTLEMENT. Zmiana:

* Faza PARTICIPATION: zamiast tylko pokazywać naruszenia, dodaj link/akcję "Rozpocznij kwalifikację" lub "Kontynuuj kwalifikację" lub "Zobacz decyzję".
* Faza BIDDING: jeśli naruszenie to `PARTICIPATION_DECISION_GRANTED` (brak), pokaż "Najpierw przejdź kwalifikację w fazie PARTICIPATION powyżej".

=== Document Submit ↔ Statements

Oświadczenia i dokumenty to różne byty (zgodnie z ADR):

* Oświadczenia: w wizardzie, przed licytacją.
* Dokumenty: w dotychczasowym formularzu DocumentSubmitComponent, na każdym etapie.

Nie łączymy ich w jeden formularz, ale wizualnie pokazujemy relację:

=== Nowy Mapper (participation-view.mapper.ts)

Mapper transformuje wygenerowane typy na VM z polskimi labelkami:

* `StatementProgramViewStatusEnum.IN_PROGRESS` → `'Kwalifikacja w toku'`
* `ParticipationDecisionViewStatusEnum.ADMITTED` → `'Dopuszczony'`
* `StatementStepViewAnswerTypeEnum.YES_NO` → `'Tak / Nie'`
* Template labels: mapowanie `templateName` → polska nazwa + opis
* Progress computed: `completedStatements.length / (available + completed + blocked).length`
* Grupowanie oświadczeń po `order` + `stepLabel`

== Wymagane zmiany backend

=== 1. Rozszerzenie CreateAuctionRequest

Obecny `CreateAuctionRequest` w OpenAPI:

....
CreateAuctionRequest:
  type: object
  required: [title, startingPrice, endsAt]
  properties:
    title: { type: string }
    startingPrice: { $ref: '#/components/schemas/Money' }
    endsAt: { type: string, format: date-time }
    buyNowPrice: { $ref: '#/components/schemas/Money' }
    lotId: { type: string, format: uuid }
    pricingConfig: { $ref: '#/components/schemas/PricingConfig' }
....

Brakuje:

....
    auctionFormat:
      type: string
      enum: [ENGLISH_ASCENDING, DUTCH_DESCENDING, SEALED_BID, RESTRICTED_TENDER, MULTI_LOT_COMBINATORIAL]
      default: ENGLISH_ASCENDING
    participationPolicyTemplate:
      type: string
      default: PUBLIC_CONSUMER_LIGHT_V1
....

To wymaga:

. Dodania pól do OpenAPI YAML
. Regeneracji TypeScript i Java
. Dodania pól do `AuctionJpaEntity`
. Dodania pól do domeny `Auction`
. Ustawienia template'u przy tworzeniu aukcji

=== 2. Endpoint listowania szablonów

Obecnie `PolicyTemplateCatalog` jest statyczny w Javie. UI musi wiedzieć, jakie szablony są dostępne i jakie mają parametry.

Propozycja nowego endpointu:

....
GET /api/participation-templates
200:
  content:
    application/json:
      schema:
        type: array
        items:
          type: object
          properties:
            templateName: { type: string }
            label: { type: string }
            description: { type: string }
            statementCount: { type: integer }
            steps:
              type: array
              items:
                type: object
                properties:
                  order: { type: integer }
                  stepLabel: { type: string }
                  statementCodes: { type: array, items: { type: string } }
....

Alternatywa: Hardcode listę szablonów w frontendzie (ponieważ są statyczne). Jest to akceptowalne na tym etapie, bo szablony są zdefiniowane w kodzie Java, nie w bazie.

**Rekomendacja**: Hardcode na etapie MVP. Endpoint dodać, gdy szablony będą dynamiczne (zapisywane w bazie przez administratora).

=== 3. Association: Auction → Template

Obecnie `StartParticipationProgramRequest` wymaga `templateName` od klienta. To znaczy, że licytant sam wybiera szablon.

Docelowo: aukcja powinna mieć przypisany szablon. Licytant nie powinien wybierać -- to organizator decyduje o poziomie kwalifikacji.

**Rekomendacja na MVP**: Dodanie `participationPolicyTemplate` do `CreateAuctionRequest`. Przy `startProgram` frontend automatycznie używa szablonu przypisanego do aukcji (zamiast pytania licytanta).

To wymaga dodania pola do `AuctionResponse`:

....
    participationPolicyTemplate:
      type: string
      description: Name of the participation policy template assigned to this auction
....

== Mapowanie odpowiedzi YES_NO

Dla `answerType = YES_NO`, UI pokazuje "Tak" / "Nie", ale API oczekuje `answerValue` jako string.

Konwencja:

* "Tak" → `"YES"`
* "Nie" → `"NO"`

To jest spójne z backendem, gdzie `DisqualifyingAnswer` ma `answerValue = "NO"` dla oświadczeń z `AnswerType.YES_NO`.

**Ważne UX**: Oświadczenia z `severity = BLOCKING` i odpowiedzią "Nie" jako dyskwalifikującą powinny mieć ostrzeżenie przy opcji "Nie":

....
⚠️ Odpowiedź "Nie" powoduje natychmiastowe odrzucenie z aukcji.
....

To jest krytyczne dla UX -- użytkownik musi wiedzieć o konsekwencji PRZED kliknięciem.

== Sygnalizacja wagi oświadczenia

Każde oświadczenie ma `severity` (z `StatementDefinition`), ale obecnie `StatementStepView` w OpenAPI nie przekazuje tego pola.

**Opcja A**: Rozszerzyć `StatementStepView` o pole `severity`.
**Opcja B**: Hardcode mapowanie `statementCode → severity` w frontendzie na podstawie `PolicyTemplateCatalog`.

**Rekomendacja**: Opcja A dla pełnej poprawności. Opcja B jako fallback MVP.

Severniness UI:

| Severity | Wizualizacja |
|----------|-------------|
| `BLOCKING` | Czerwona ramka + ostrzeżenie + "Odpowiedź powoduje wykluczenie" |
| `IMPORTANT` | Żółta ramka + informacja + "Odpowiedź będzie wymagała weryfikacji" |
| `INFORMATIONAL` | Standardowa ramka + "Odpowiedź ma charakter informacyjny" |
