== Kontekst i Motywacja

Hexabid obecnie ma reguly zakodowane na sztywno jako if-y w 3 miejscach:

|===
|Miejsce |Co robi |Problem

|`CreateAuctionService` |`kycClient.isVerified(sellerId)` |Jedna regula, zero konfiguracji
|`PlaceBidService` |`kycClient.isVerified(bidderId)` + `auction.placeBid()` |Brak wadium, brak pelnoletnosci, brak dokumentow
|`CloseExpiredAuctionsService` |Zamyka aukcje |Brak regul po-wygranej (dokumenty, terminy)
|===

Cykl zycia aukcji to `OPEN -> CLOSED` -- za malo stanow na proces rozliczeniowy.

=== Przyklady regul biznesowych do obsluzenia

* Nieruchomosc -> termin ogledzin przy definiowaniu produktu
* Wartosc > 10k PLN -> wadium 10% od szacowanej ceny
* Alkohol/tyton -> pelnoletnosc
* Akcyza -> kopia dokumentu do przystapienia, oryginal po wygranej
* Clo -> kopia zwolnienia do przystapienia, oryginal po wygranej
* Nieruchomosc po wygranej -> oryginal dokumentu XYZ w ciagu 3 dni
* Zwolniony z oplat celnych -> mozna przystapic z kopia, ale oryginal po wygranej

=== 1.3 Algebra -- Rozdzielenie struktury od ewaluacji

To jest **kluczowy wzorzec z M04L05**: Bridge pattern miedzy Expression (struktura) a Algebra (ewaluacja).

```java
// algebra/RuleAlgebra.java
public interface RuleAlgebra<R> {
    R and(R left, R right);
    R or(R left, R right);
    R not(R inner);
    R ifThenElse(R condition, R thenResult, R elseResult);
    R constant(boolean value);
    R attributeCheck(AttributeKey key, AttributeCheck.Comparator cmp, Object value);
    R metricComparison(AttributeKey metric, AttributeCheck.Comparator cmp, Object threshold);
}
```

**BooleanAlgebra** -- ewaluacja warunkow (czy regula jest aktywna):

```java
// algebra/BooleanAlgebra.java
public final class BooleanAlgebra implements RuleAlgebra<Boolean> {
    @Override
    public Boolean and(Boolean left, Boolean right) { return left && right; }
    @Override
    public Boolean or(Boolean left, Boolean right) { return left || right; }
    @Override
    public Boolean not(Boolean inner) { return !inner; }
    @Override
    public Boolean ifThenElse(Boolean cond, Boolean thenR, Boolean elseR) {
        return cond ? thenR : elseR;
    }
    @Override
    public Boolean constant(boolean value) { return value; }
    @Override
    public Boolean attributeCheck(AttributeKey key, Comparator cmp, Object value) {
        // Ekstrakcja z RuleContext i porownanie
    }
    // ...
}
```

**ComplianceAlgebra** -- ewaluacja zgodnosci (SATISFIED / PENDING / VIOLATED):

To jest trójwartosciowa algebra. Kluczowa logika:

```
and(SATISFIED, SATISFIED)     = SATISFIED
and(SATISFIED, PENDING)      = PENDING
and(SATISFIED, VIOLATED)     = VIOLATED
and(PENDING, VIOLATED)       = VIOLATED   -- VIOLATED dominuje
and(PENDING, PENDING)        = PENDING

or(SATISFIED, _)             = SATISFIED  -- SATISFIED dominuje
or(PENDING, SATISFIED)       = SATISFIED
or(VIOLATED, SATISFIED)      = SATISFIED
or(VIOLATED, PENDING)        = PENDING
or(VIOLATED, VIOLATED)       = VIOLATED

not(SATISFIED)               = VIOLATED
not(VIOLATED)                = SATISFIED
not(PENDING)                 = PENDING
```

**ExplainedAlgebra** -- ewaluacja z wyjasnieniami (receipt dla biznesu):

=== 1.4 ExpressionVisitor -- Bridge miedzy AST a Algebra

Bazowane na `AlgebraicVisitor` z archetypu:

```java
// ast/ExpressionVisitor.java
public class ExpressionVisitor<R> {
    private final RuleAlgebra<R> algebra;
    private final RuleContext context;

    public ExpressionVisitor(RuleAlgebra<R> algebra, RuleContext context) {
        this.algebra = algebra;
        this.context = context;
    }

    public R evaluate(Expression expr) {
        return switch (expr) {
            case AttributeCheck ac -> algebra.attributeCheck(ac.key(), ac.comparator(), ac.value());
            case AndExpression and -> algebra.and(evaluate(and.left()), evaluate(and.right()));
            case OrExpression or -> algebra.or(evaluate(or.left()), evaluate(or.right()));
            case NotExpression not -> algebra.not(evaluate(not.inner()));
            case IfThenElse ite -> {
                var condResult = evaluate(ite.condition());
                // Uzywamy algebry do warunkowego rozgalezienia
                yield algebra.ifThenElse(condResult, evaluate(ite.thenExpr()), evaluate(ite.elseExpr()));
            }
            case ConstantExpression ce -> algebra.constant(ce.value());
            case MetricComparison mc -> algebra.metricComparison(mc.metric(), mc.comparator(), mc.threshold());
        };
    }
}
```

```java
// engine/RuleCatalog.java
public final class RuleCatalog {
    private final List<RuleDefinition> rules;

    public RuleCatalog() { this.rules = new ArrayList<>(); }

    public void register(RuleDefinition rule) { rules.add(rule); }

    public List<RuleDefinition> rulesForPhase(RulePhase phase) {
        return rules.stream().filter(r -> r.phase() == phase).toList();
    }

    public List<RuleDefinition> applicableRules(RulePhase phase, RuleContext context) {
        var visitor = new ExpressionVisitor<>(new BooleanAlgebra(), context);
        return rules.stream()
            .filter(r -> r.phase() == phase)
            .filter(r -> visitor.evaluate(r.applicabilityCondition()))
            .toList();
    }
}
```

=== 1.7 RuleEngine -- Fasada

```java
// engine/RuleEngine.java
public final class RuleEngine {
    private final RuleCatalog catalog;

    public RuleEngine(RuleCatalog catalog) { this.catalog = catalog; }

    public List<RuleEvaluationResult> evaluateAll(RulePhase phase, RuleContext context) {
        var applicableRules = catalog.applicableRules(phase, context);
        var algebra = new ComplianceAlgebra();
        var results = new ArrayList<RuleEvaluationResult>();

        for (var rule : applicableRules) {
            var visitor = new ExpressionVisitor<>(algebra, context);
            var result = visitor.evaluate(rule.ruleCondition());
            results.add(mapResult(rule, result));
        }
        return results;
    }

    public ExplainedEvaluation evaluateWithExplanation(RulePhase phase, RuleContext context) {
        var applicableRules = catalog.applicableRules(phase, context);
        var algebra = new ExplainedAlgebra();
        var explanations = new ArrayList<ExplainedResult>();

        for (var rule : applicableRules) {
            var visitor = new ExpressionVisitor<>(algebra, context);
            var result = visitor.evaluate(rule.ruleCondition());
            explanations.add(result);
        }
        return new ExplainedEvaluation(explanations);
    }

    public boolean hasBlockingViolations(RulePhase phase, RuleContext context) {
        return evaluateAll(phase, context).stream()
            .anyMatch(r -> r instanceof Violated v && v.severity() == RuleSeverity.BLOCKING);
    }
}
```

== FAZA 2: Rozszerzenie Cyklu Zycia Aukcji

=== 2.1 Obecny stan

```
[creation] -> OPEN -> CLOSED
```

Dwa stany, jedno przejscie. Brak rozliczenia, brak draftu, brak anulowania.

=== 2.2 Docelowy cykl zycia

```
DRAFT -> PUBLISHED -> IN_PROGRESS -> PENDING_SETTLEMENT -> SETTLED
                                         |                     ^
                                         v                     |
                                    FAILED_SETTLEMENT ---------+
                                         |
                                         v
                                    REOFFERED
```

|===
|Stan |Znaczenie |Reguly ewaluowane |Kto inicjuje przejscie

|`DRAFT` |Aukcja tworzona, niewidoczna |ParticipationRules przy publikacji |Sprzedajacy
|`PUBLISHED` |Widoczna, ale jeszcze nie trwa |Brak |Scheduler (termin rozpoczecia)
|`IN_PROGRESS` |Trwa licytacja |BiddingRules przy kazdym bid |Uczestnicy (placeBid)
|`PENDING_SETTLEMENT` |Zakonczona z wygrywajacym, czeka na rozliczenie |SettlementRules z deadline'ami |Scheduler (closeExpired)
|`SETTLED` |Wszystkie obowiazki spelnione |Brak |SettleAuctionService
|`FAILED_SETTLEMENT` |Wygrany nie spelnil obowiazkow |Reguly ponownej aukcji |SettlementDeadlineJob
|`REOFFERED` |Ponownie wystawiona (dla kolejnego biddera lub nowa aukcja) |ParticipationRules |SettleAuctionService
|===

=== 2.6 ReservePrice -- egzekwowanie (bug fix)

Obecnie `Lot.reservePrice` nie jest sprawdzane w `Auction.placeBid()` ani w `maybeCloseIfExpired()`.

**Poprawka w `Auction.closeWithWinner()`:**

```java
public AuctionEvent closeWithWinner(Instant closedAt) {
    ensureStatusIs(IN_PROGRESS);
    var leadingBid = maybeLeadingBid().orElseThrow();
    if (leadingBid.amount().isLessThan(lot.reservePrice())) {
        // Wygrywajaca oferta ponizej ceny rezerwowej
        // Emitujemy zdarzenie ale NIE przechodzimy do PENDING_SETTLEMENT
        return new AuctionClosedBelowReserveEvent(id, leadingBid.amount(), lot.reservePrice(), closedAt);
    }
    status = AuctionStatus.PENDING_SETTLEMENT;
    return new AuctionWonEvent(id, leadingBid.bidderId(), leadingBid.amount(), closedAt, settlementDeadline, requiredDocuments);
}
```

=== 2.7 Zmiany w PlaceBidService

Obecny `PlaceBidService` sprawdza tylko KYC i deleguje do `auction.placeBid()`.
Po zmianach:

```java
// Nowy przebieg PlaceBidService.placeBid():

1. Sprawdz KYC biddera (istniejace)
2. Znajdz aukcje (istniejace)
3. NOWE: Sprawdz czy aukcja jest w statusie IN_PROGRESS (nie PUBLISHED, nie DRAFT)
4. NOWE: Ewaluuj BiddingRules przez AuctionRuleEvaluator
   - Zbuduj RuleContext z danych aukcji i biddera
   - Jezeli BLOCKING violation -> odrzuc bid z odpowiednim powodem
5. Deleguj do auction.placeBid() (istniejace)
```

=== 2.8 Nowy: SettleAuctionService

```java
// hexabid-core: usecase/SettleAuctionService.java
public final class SettleAuctionService implements SettleAuctionUseCase {

    private final AuctionRepository auctionRepository;
    private final AuctionRuleEvaluator ruleEvaluator;
    private final AuctionEventPublisher eventPublisher;
    private final Clock clock;

    public SettlementResult settleAuction(AuctionId auctionId) {
        var auction = auctionRepository.findById(auctionId)
            .orElseThrow();

        // Zbuduj RuleContext z danych aukcji i wygranego
        var context = buildSettlementContext(auction);

        // Ewaluuj SettlementRules
        var results = ruleEvaluator.evaluateSettlementRules(context);

        // Sprawdz czy sa BLOCKING violations
        if (hasBlockingViolations(results)) {
            auction.markSettlementFailed("Blocking violations: " + summarizeViolations(results));
            auctionRepository.save(auction);
            return SettlementResult.failed(results);
        }

        // Wszystko spelnione -> rozlicz
        auction.markAsSettled();
        auctionRepository.save(auction);
        return SettlementResult.succeeded();
    }
}
```

== FAZA 3: Konkretne Reguly Biznesowe

=== 3.1 Spis regul z mapowaniem na model

Kazda regula jest zdefiniowana jako `RuleDefinition` z:
- **applicabilityCondition** -- Expression okreslajace KIEDY regula dotyczy aukcji
- **ruleCondition** -- Expression okreslajace CZY regula jest spelniona
- **phase** -- na jakim etapie cyklu aukcji
- **severity** -- czy blokuje, ostrzega, czy informuje

==== Reguly fazy PARTICIPATION (czy moge przystapic?)

|===
|Regula |Applicability Condition |Rule Condition |Severity |Violated Message

|Wadium 10% powyzej 10k PLN |`estimatedValue > 10000 AND productType != REAL_ESTATE` |`wadiumPaid == true` |BLOCKING |Wadium 10% wartosci szacunkowej jest wymagane

|Termin ogledzin nieruchomosci |`productType == REAL_ESTATE` |`viewingDateScheduled == true` |BLOCKING |Dla nieruchomosci wymagane jest zdefiniowanie terminu ogledzin

|Pelnoletnosc (alkohol/tyton) |`productType IN (ALCOHOL, TOBACCO)` |`bidderAge >= 18` |BLOCKING |Wymagana pelnoletnosc do zakupu tego produktu

|Kopia dokumentu akcyzy do przystapienia |`excisable == true` |`exciseDocumentStatus == COPY OR exciseDocumentStatus == ORIGINAL` |WARNING |Dostarcz kopie dokumentu akcyzy. Oryginal bedzie wymagany po wygranej

|Kopia zwolnienia celnego do przystapienia |`imported == true AND customsExempt == true` |`customsExemptionDocStatus == COPY OR customsExemptionDocStatus == ORIGINAL` |WARNING |Dostarcz kopie zwolnienia celnego. Oryginal bedzie wymagany po wygranej

|Wadium 10% dla nieruchomosci |`productType == REAL_ESTATE` |`wadiumPaid == true` |BLOCKING |Dla nieruchomosci wadium 10% jest wymagane przed licytacja
|===

==== Reguly fazy BIDDING (czy moge licytowac?)

|===
|Regula |Applicability Condition |Rule Condition |Severity |Violated Message

|Wadium wpłacone |`estimatedValue > 10000 OR productType == REAL_ESTATE` |`wadiumPaid == true` |BLOCKING |Nie mozna licytowac bez wplate wadium

|KYC zweryfikowany |Zawsze (AlwaysTrue) |`kycVerified == true` |BLOCKING |Wymagana weryfikacja KYC
|===

==== Reguly fazy SETTLEMENT (co po wygranej?)

|===
|Regula |Applicability Condition |Rule Condition |Severity |Violated Message

|Oryginal dokumentu akcyzy |`excisable == true` |`exciseDocumentStatus == ORIGINAL` |BLOCKING |Wymagany oryginal dokumentu akcyzy do rozliczenia

|Oryginal zwolnienia celnego |`imported == true AND customsExempt == true` |`customsExemptionDocStatus == ORIGINAL` |BLOCKING |Wymagany oryginal zwolnienia celnego do rozliczenia

|Dokument XYZ w 3 dni (nieruchomosc) |`productType == REAL_ESTATE` |`settlementDocumentProvided == true AND daysSinceClose <= 3` |BLOCKING |Dla nieruchomosci wymagany oryginal dokumentu w ciagu 3 dni roboczych

|Platnosc pelnej kwoty |Zawsze (AlwaysTrue) |`fullPaymentReceived == true` |BLOCKING |Wymagana platnosc pelnej kwoty do rozliczenia

|Potwierdzenie odbioru |`productType != REAL_ESTATE` |`receiptConfirmed == true` |WARNING |Potwierdzenie odbioru towaru
|===

=== 3.2 Kluczowy wzorzec: ten sam dokument, rozne wymagania na roznych etapach

To jest wprost z M04L02 (Three-zone logic model): "ten sam koncept, rozna ostrosc na roznych etapach"

```
Dokument akcyzy:
  PARTICIPATION -> kopia wystarczy  (WARNING: mozna licytowac)
  SETTLEMENT    -> oryginal wymagany (BLOCKING: nie rozliczysz bez tego)

Zwolnienie celne:
  PARTICIPATION -> kopia wystarczy  (WARNING)
  SETTLEMENT    -> oryginal wymagany (BLOCKING)
```

To jest realizowane przez **dwie osobne reguly** w `RuleCatalog`:
1. `EXCISE_DOCUMENT_COPY_PARTICIPATION` (phase=PARTICIPATION, severity=WARNING)
2. `EXCISE_DOCUMENT_ORIGINAL_SETTLEMENT` (phase=SETTLEMENT, severity=BLOCKING)

Obie dotycza tego samego `AttributeKey.EXCISE_DOCUMENT_STATUS`, ale z roznymi comparatorami.

== FAZA 5: Graf Procesu (User Journey) -- Opcjonalne Rozszerzenie

=== 5.1 Motywacja

Po Fazach 1-4 reguly sa ewaluowane punktowo (na konkretny event).
Faza 5 wprowadza **perspektywe procesowa** -- graf stanow i przejsc,
ktory pozwala odpowiedziec na pytania biznesowe:

* "Co musze zrobic, zeby uztawic aukcje nieruchomosci?" -> path query w grafie
* "Czy moge przystapic do tej aukcji?" -> reachability check
* "Jaki jest najszybszy sposob na rozliczenie?" -> shortest path
* "Co blokuje rozliczenie tej aukcji?" -> articulation points / pending requirements

To jest dokladnie wzorzec z **M05L04** (User Story Archetype: Processes as State/Transition Graphs).

=== 5.2 AuctionProcessGraph

Nowa klasa w `hexabid-rules` (lub osobny modul `hexabid-rules-graph`):

```java
// graph/AuctionProcessGraph.java
public final class AuctionProcessGraph {

    // Graf stanow: node = AuctionStatus, edge = Transition (condition + requiredAction)
    private final Map<AuctionStatus, List<Transition>> transitions;

    public record Transition(
        AuctionStatus from,
        AuctionStatus to,
        String description,       // "Wplac wadium", "Dostarcz oryginal akcyzy"
        RulePhase requiredPhase, // PARTICIPATION, BIDDING, SETTLEMENT
        Expression condition     // warunek przejscia (z AST)
    ) {}

    // Pytania do grafu:

    /** Jakie akcje sa wymagane do przejscia z A do B? */
    public List<Transition> requiredActions(AuctionStatus from, AuctionStatus to);

    /** Czy z obecnego stanu i kontekstu mozna osiagnac cel? (reachability) */
    public boolean canReach(AuctionStatus current, AuctionStatus target, RuleContext context);

    /** Jakie przejscia sa mozliwe z obecnego stanu? (dostepne akcje) */
    public List<Transition> availableTransitions(AuctionStatus current, RuleContext context);

    /** Jaka jest najkrotsza sciezka do rozliczenia? (shortest path) */
    public List<Transition> shortestPathToSettlement(AuctionStatus current, RuleContext context);

    /** Co blokuje przejscie do nastepnego stanu? (blocking violations) */
    public List<Violation> blockingViolations(AuctionStatus current, RuleContext context);
}
```

=== 5.3 Przyklad grafu dla nieruchomosci

```
DRAFT
  |
  | [Zdefiniuj termin ogledzin]     <-- ParticipationRule: VIEWING_DATE_REAL_ESTATE
  | [Wplac wadium 10%]              <-- ParticipationRule: WADIUM_REAL_ESTATE
  v
PUBLISHED
  |
  | [Poczekaj na termin rozpoczecia]
  v
IN_PROGRESS
  |
  | [Zwycieska oferta >= reservePrice]
  v
PENDING_SETTLEMENT
  |
  | [Dostarcz oryginal dokumentu XYZ w 3 dni] <-- SettlementRule: REAL_ESTATE_DOCUMENT_3_DAYS
  | [Dokonaj platnosci pelnej kwoty]           <-- SettlementRule: FULL_PAYMENT_SETTLEMENT
  v
SETTLED
```

Pytania do grafu:

* `canReach(DRAFT, SETTLED, context)` -> sprawdz czy wszystkie reguly PARTICIPATION + SETTLEMENT sa osiagalne
* `blockingViolations(PENDING_SETTLEMENT, context)` -> "Brak oryginalu dokumentu XYZ", "Brak platnosci"
* `shortestPathToSettlement(PENDING_SETTLEMENT, context)` -> [dostarcz dokument, zaplac]

=== 5.5 Implementacja techniczna

Do implementacji grafu mozna uzyc:

1. **JGraphT** (jak w archetypie `graphs`) -- pelna biblioteka grafowa z gotowymi algorytmami
2. **Wlasna implementacja** (jak w archetypie `cycles/math/Graph.java`) -- prostsza, bez zaleznosci

Rekomendacja: **JGraphT** -- algorytmy (shortest path, reachability, topological sort) sa gotowe.
Zaleznosc tylko w `hexabid-rules` (lub `hexabid-rules-graph`), nie w core.

```xml
<!-- hexabid-rules-graph/pom.xml -->
<dependency>
    <groupId>org.jgrapht</groupId>
    <artifactId>jgrapht-core</artifactId>
    <version>1.5.2</version>
</dependency>
```

=== 5.6 Wartosc edukacyjna

Faza 5 jest **najlepszym material edukacyjny** w calej implementacji:
laczy 3 archetypy w jednym zastosowaniu:

* **M04 (Rules)** -- reguly jako AST z wymiennym Algebra
* **M05 (Graphs)** -- proces jako state/transition graph z zapytaniami
* **M02 (Product)** -- ApplicabilityConstraint decyduje ktore reguly dotycza produktu

Pokazuje tez wzorzec z M05L04: **kazde nowe zachowanie jest addytywne**
(nowy typ produktu = nowe krawedzie w grafie, nie modyfikacja istniejacego kodu).

=== Kryteria akceptacji per faza

**Faza 1:**

* `RuleEngine.evaluateAll()` dziala z `BooleanAlgebra` i `ComplianceAlgebra`
* `ExpressionVisitor` przechodzi kazdy typ wezla AST
* `RuleCatalog` filtruje reguly po phase i applicability
* Wszystkie testy przechodza
* Brak zaleznosci od Spring/JPA (czysty Java)

**Faza 2:**

* `AuctionStatus` ma 7 stanow
* Nowe przejscia dzialaja: DRAFT -> PUBLISHED -> IN_PROGRESS -> PENDING_SETTLEMENT -> SETTLED
* `Lot.reservePrice` jest egzekwowane w `closeWithWinner()`
* Nowe domain events: AuctionPublishedEvent, AuctionStartedEvent, AuctionClosedBelowReserveEvent, AuctionSettledEvent, AuctionSettlementFailedEvent
* ArchUnit test przechodzi

**Faza 3:**

* Wszystkie reguly z sekcji 3.1 sa zaimplementowane jako RuleDefinition
* `RuleContext` builder dziala dla Participation, Bidding, Settlement
* `DocumentRequirement` i `DocumentStatus` modele istnieja
* Nowe porty: `DocumentRepository`, `WadiumDepositPort`

**Faza 4:**

* `RuleEvaluatorAdapter` laczy core z rules
* `CreateAuctionService` ewaluuje ParticipationRules
* `PlaceBidService` ewaluuje BiddingRules
* `SettleAuctionService` ewaluuje SettlementRules
* Nowe endpointy REST dla rozliczenia i dokumentow
* Integration test: pelny cykl aukcji z regulami

**Faza 5:**

* `AuctionProcessGraph` odpowiada na pytania path/reachability/blocking
* JGraphT zintegrowany w hexabid-rules-graph
* Wizualizacja grafu procesu (optional: endpoint REST zwracajacy strukture grafu)
